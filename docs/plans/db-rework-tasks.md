# Tasks: database rework (v1.1)

Status: started 1 Nov 2026 on `releases/v1.1`. The design is in the code (`internal/migrate/sql/space/0001_base.sql`) and `docs/split-payments.md`; this file is the order of work. Nothing is committed by the agent: the owner commits and reviews between tasks.

Rules for every task:

- Tests cover Go logic (repositories, ledger rules, conversion), not the SQL schema itself: no tests that check a CHECK or foreign key does what SQLite says.
- New or changed query: add the `.sql`, run `go generate ./internal/db`, add the repo method, test it with `db/dbtest` (see `internal/db/AGENTS.md`).
- User-visible change: update `docs/`.
- `go generate ./internal/db` pins sqlc v1.31.1 (`internal/db/generate.go`), which types `EXISTS` as `bool`.

**3. Categories, budgets and reports.** `categories.sql` counts and reassigns through `transaction_lines`; `internal/db/filter` report aggregates (`SumByType`, `SumGroupedByCategory`, `DailyTotals`, `GroupedByPeriod`, `TopTransactions`, `BudgetSpent`) sum lines in the line's own currency. A line is income or expense by its category's type (an uncategorised line by its transaction's type), so a transfer's fee line is spending and a debt transaction is skipped; a transaction counts once per day however many lines it has; an account filter matches any payment. `ListAccounts` has `exclude_space` and `ledger.Accounts.ForNetWorth` lists ordinary accounts and debts for `reports/networth.go`. **4. Recurring rules and transfers.** `recurring.sql`: a rule is `template` plus `schedule` plus `is_active` and `error`; `recurring_instances` holds the handled due dates (`last_due`, `last_run` and `pending_due` are derived in the query). `internal/recurring` no longer imports `ledger`: it keeps the template as opaque JSON and reaches the ledger through the `Occurrences` interface (`Validate`, `Create`, `Replan`, each on the handle it is given), which task 5 implements. `Schedule` (`schedule.go`) is parsed and validated; the next due date is the open occurrence's, else one step after the latest handled one, else `start`; `AdvanceAfterOccurrence(ctx, d, rule)` takes the handle of the confirming transaction; `EnsureUpcoming` first stops every active rule whose schedule or template does not validate (`is_active = 0`, reason in `error`), then makes the missing occurrences. Deleting a rule keeps its pending transaction. `transfers.sql`: a record is `payload` (the signed bytes, kept in `Transfer.signed` and verified as stored) plus `remote`, status `confirmed` or `in_review`; the review kind is derived from which of the two exist (`records.go`); `SaveMirror` writes the transaction of a side with the real payment and the space-account payment that carries the uuid, in place on update, and makes the space account of the currency when missing; a service account is refused as a side (`ErrServiceAccount`); `View.NeedsAttention` replaces the stored `needs_attention`. Fixed in `0001_base.sql`: the generated `source` and `destination` read `$.from.space` and `$.to.space`, the keys of the signed payload (they read `space_uuid`, so were always NULL). Tests: `db/repo/recurring`, `db/repo/transfers` (mirror, record shape), `internal/recurring` (schedule table tests, service on a fake ledger over the real repo), `internal/transfers` (mirror per side, stored bytes, review kinds and accepting). Not done, because they wait for task 5: `boot/jobs.go`, `httpserver/scope.go`, `seed/rules.go` and `api/recurring` still use the old `Recurring`/`Input`; `ledger` must call `Recurring.AdvanceAfterOccurrence` from confirm, skip and delete in the same database transaction (`RuleOf` finds the rule of a transaction); the amount-range check of `amount_test.go` (removed) belongs in the ledger's template validation. `legacy` and the v1.0 `TestP21LaravelBackup` still fail on the base schema until task 7.

**5. Ledger rules and the API.** `internal/ledger`: `TxInput` (type, description, date, `payments`, `lines`, `tag_ids`) is also the JSON of a recurring template; `Transaction` has `Payments`, `Lines`, `Reasons`, `Amount()` and, on the answer to a save, `Difference`. `shape.go` holds the ledger checks (one payment per account, no payment of 0, net sign, line category type and currency, transfer signs and fee lines, debt and space-account shapes, one payment without an amount in a template) and the soft check, which never fails a save. `restrict.go` is the one map from reason to actions (`debt`, `space_transfer`, `transfer_review`, `recurring_pending`); `Allowed()` is the ERD matrix, a table test in `allowed_test.go`. A module acts through `Transactions.As(reason)`: debts (`Debts.record` writes two payments, the ordinary one converted when currencies differ), transfers (sets `PaymentInput.SpaceTransferUUID`), and `Templates` (`Validate`, `Create`, `Replan`; implements `recurring.Occurrences`, fills the empty payment at that day's rates). Groups, items and `guardRow` are gone. A repo query (`ListTransactionLinks`) loads the transfer status and rule id with the page. API: strict body (an unknown key such as `account_id` is a 422), `payments` and `lines` in the answer with `restrictions`, confirm and skip advance the rule in the same database transaction (`settle`), `/transaction-groups` and the `*_transaction_group` MCP tools removed, `/recurring` takes `template` and `schedule`. Seed, importer tests, reports tests and automation (`amount` is the payments' net in one currency, `account_id` and `category_id` match any payment or line, `set_category` fills uncategorised lines only; `create_transfer` converts at current rates via `Transactions.ConvertedTransfer`) moved to the new input. The seed's credit card is an ordinary account now, and its monthly rule no longer repeats the mortgage payment (a rule creates only what can be entered by hand). `docs/api.md`, `docs/mcp.md` updated; `docs/split-payments.md` only points to them until task 6. **7. v1.0 converter.** `internal/migrate/upgrade/v1`: `Convert(ctx, src, dst, up)` writes a fresh file from the current base (`up` is `migrate.Space.Up`, passed in because migrate's tests import this package) and copies a v1.0 file into it in one transaction, (the mapping is in `internal/migrate/upgrade/v1`); `IsV1` tells a v1.0 file by `schema_migrations`; `Apply` and `EnsureIndexes` give a file the frozen v1.0 schema. Transfers are rebuilt in Go from a frozen `payloadV1` (the signed bytes, `<`, `>` and `&` escaped); recurring rules get a `template` and `schedule` from frozen structs (amounts as decimal strings by the account's decimals; an amount of 0 or a transfer's missing `to_amount` stays empty; a day that does not fit the frequency is dropped; the pending occurrence is due on `next_run_date`). A debt's `principal` is the target, else what was issued, else 1; `initial_balance` is +-(principal - issued). Space accounts are named `Other spaces · CODE`. Where it runs: `store/sqlite` `openSpace` converts a v1.0 file before opening it (`upgrade.go`: the v1.0 file is checkpointed and kept as `<id>.sqlite.v1.1`, the result is renamed over it, so a crash leaves the original); `sanitize` for a v1.0 space source sanitizes it into a v1.0 file of our own and converts that (an upload, a server backup, a Laravel restore); `legacy` now gives the Laravel file the frozen v1.0 space schema (`v1.Apply`) instead of the base, and `knownVersions` accepts `space/0001_initial`. Tests: `migrate/v1/convert_test.go` (a fixture with every row kind, decoded with the real `ledger.TxInput` and `recurring.ParseSchedule`), `store/sqlite/upgrade_v1_test.go` (start, upload), `legacy` and the Laravel restore tests. Also fixed here: the `archtest` limits and the `httpserver` transfer tests, which still expected the v1.0 statuses (`ok`, `pending`, `needs_attention`) and the flat transaction body. Not done: the space key is not generated (task 8 makes keys at creation and for converted spaces, so it must also run for a space that was converted before it exists); `docs/` do not mention the upgrade yet (task 6); the converter has no check that balances equal the v1.0 ones, because v1.0 added `COALESCE(to_amount, 0)` to a transfer's destination and the plan uses `COALESCE(to_amount, amount)`.

**8. Signing with space keys.** `internal/spacekeys` (`Current` makes the key when a space has none, `Rotate`, `Public`) over `db/repo/spacekeys` (`space_keys`; adding a key retires the current one). `spaces.Service` makes the key at `Create` and `CreateFrom`; a space imported under a new uuid gets a key of its own (`Rotate`), so a copy never signs as its source. A `sig_v` 2 transfer keeps the `transferPayloadV1` bytes and is signed by the source space's key (`source_*`) and the destination's (`destination_*`; `Transfer.DestKID`, `DestSignature`, also in the `remote` JSON). `signing.go`: `signWithSpaces` signs inside the `InSpaces` of the write (both handles, so a missing key is made in that transaction), `signStored` keeps stored bytes; `verifier` reads each space's keys (current and retired) from its live file, so a transfer verifies only while both spaces are here (`Service.verify` outside `InSpaces`, the sync's verifier inside); `sig_v` 1 still verifies by the server ring. `Trust` re-signs with the space keys and needs both spaces here (`ErrSpaceMissing`). At startup (`boot/startup.go`): `EnsureKeys` (also covers spaces the converter made and old backups), `SyncAll`, then `Resign` (`spacesign.go`): a `sig_v` 1 transfer whose server signature verifies and that both spaces hold alike and confirmed becomes `sig_v` 2 over the same bytes, written to both spaces in one step. The converter does not make a key (`EnsureKeys` does). Tests: `transfers_test.go` (both keys sign, one signature is not enough, space key rotation, key at creation, `EnsureKeys`, `Resign`, spaces moved together keep their transfers, one moved space is frozen, a forged transfer fails the other space's key, `Trust`), `db/repo/spacekeys`. `docs/spaces.md` and `docs/data-and-backups.md` updated. Not done: no API or UI to rotate a space key (only `spacekeys.Rotate`); the server key's admin screens still say it signs transfers in their texts, if any; `archtest` still fails on two names in `migrate/upgrade/upgrade_test.go` (task 7, not touched here).

**10. Credit cards (backend).** `accounts.type` has `credit`; `credit_cards` (`account_id`, `credit_limit`, `cycle`, `statement_day`, `period_days`, `grace_days`) holds the terms. Only `fixed_day` is built: `ValidateCard` refuses `first_expense` (it stays in the schema because the base is frozen at release) and a grace period over 60 days. `internal/ledger/creditcard.go`: `ComputeCardState` is a pure function of the card, the opening balance, the card's `DayFlow`s (net, in and out per day, from `AccountDailyFlows`) and today; `Accounts.CardState` loads the flows. A period closes at the end of its statement day (on that day the one before is still the last statement). The status looks at the last three statements, so an unpaid one stays `danger` (`overdue`) after the next statement; `over_limit` and `payment_due` follow; the order is overdue, over limit, due. Only confirmed payments count (a pending expense does not), and days after today are left out. A card is read and written only through `ledger.CreditCards` (`Card` = `Account` + `Terms`; `Create`, `Convert` of a bank account, `Update`, `Delete`, `State`) over the `credit_cards` sidecar, as debts are through `Debts`; `Accounts` refuses `credit` (`ErrCardAccount`) and returns a card as a plain account. API: `/credit-cards` (terms flat in the body; on update, left-out keys keep their values; the answer has the derived values and `status`; `422` on the key of a bad term), token permission `accounts`; `docs/api.md` (Credit cards), `docs/mcp.md`, the OpenAPI input and the MCP argument structs. No separate alerts endpoint. Overpaying as a commission is the existing transfer fee line (test: the card sees only its own payment). Tests: `ledger/creditcard_test.go` (statement dates around month ends and leap years, balance at the statement day, partial and full payment, backdated payment, overdue carried into the next statement, over limit, future days, validation), `ledger/creditcard_account_test.go` (round trip, type rules, the commission transfer, pending ignored), `db/repo/ledger` round trip, `integration/credit_cards_test.go`, `seed/creditcard_test.go`. Seed: the demo card is `credit` (limit 15 000, statement 12 days before the seed date, 25 days grace) and is paid in full on the 25th, so it shows a warning. **Converter** (the "migration from demo data"): the v1.0 demo card was a debt with no target that money was spent from, and became a debt with principal 1 and expenses on a debt account. A v1.0 `i_owe` debt with no target, no issuance and expenses or incomes on it is now an ordinary `bank` account that starts at zero, and its debt payments become transfers (`card_debts` in `steps.go`, test `card_debt_test.go`); the user makes it a credit card by giving it terms. Not done: the frontend (task 11); `first_expense`; the converter keeps the old principal rule for every other debt.

## Tasks, in order

### 1. Accounts and debts (start here)

Smallest, self-contained area.

- Rewrite `queries/space/accounts.sql`: the debt columns (`debt_type`, `target_amount`, `due_date`, `is_paid_off`, `counterparty`, `debt_description`) leave `accounts`; add queries for `debts` (get, insert, update, close, reopen). Balances come from `payments (account_id, amount)` plus `initial_balance`, not from `transactions.account_id` and `to_account_id`.
- `Account` gets `IsService`; list queries for pickers filter `WHERE NOT is_service`.
- New repo `internal/db/repo/debts` (or a part of `ledger`, decide when reading the current debt code); `ledger` keeps the business rules.
- Space account: a query to find or create the account of type `space` for a currency.
- Decided: debts are part of the `ledger` repo (`repo/ledger/debts.go`). In `internal/ledger`, `Account` has no debt fields and `Accounts` refuses `debt` and `space` types (`ErrServiceAccount`); `Debt` (an `Account` plus `Direction`, `Principal`, `DueDate`, `Counterparty`, `Note`, `ClosedAt`) is read and written only through `Debts`. The JSON of `/debts` is unchanged.
- Done when: account balances, the account list and a debt round-trip work through the repo with tests; no query in the file touches an old column.

### 2. Transactions, payments, lines and tags

The core of the rework.

- Rewrite `queries/space/transactions.sql`: `transactions` holds facts only; add insert, replace and read for `payments` and `transaction_lines`; payments are updated in place on save (so `space_transfer_uuid` stays), lines are rewritten and renumbered from 0. Remove items, `group_uuid` and the group queries. Keep `day_order`.
- `internal/db/filter`: list filters and report grouping that read `account_id`, `amount` or `category_id` on `transactions` now read payments or lines. This is dynamic SQL and is not covered by sqlc.
- `db/repo/ledger`: new `Tx` shape (transaction, payments, lines, tags) loaded in a few queries, not one per row; `external_id` replaces `dedup_hash`.
- Done when: create, read, list with filters, update (payments in place, lines rewritten), delete and tags work through the repo with tests.

### 5. Ledger rules and the API

- `internal/ledger`: new domain types from the API's transaction input (type, description, date, payments, lines, tags). Ledger checks: a line's category type matches the transaction type; a line's currency is one of the payment accounts' currencies; the soft check compares payments and lines by current rates and only reports the difference; a payment of 0 is refused on new input; at most one payment of a recurring template may have a NULL amount.
- Restrictions: one map from reason to allowed actions (`debt`, `space_transfer`, `transfer_review`, `recurring_pending`), `Transaction.Allowed()`, loaded with the transaction. A payment on a debt or space account is allowed only through its owning module.
- API, MCP tools and the importer move to the new input. The old `isEstimated` flag becomes `estimated` on a payment in a recurring template.
- Done when: the restriction matrix from the ERD is a table test and the API returns payments and lines.

- Docs: rewrite `docs/split-payments.md`, update `docs/api.md`, `docs/mcp.md`, `docs/spaces.md` and `docs/development.md` where they show the schema; release notes (items become a note, v1.0 quantities and prices are dropped).
- Done when: `npx tsc --noEmit -p tsconfig.ci.json` and the frontend tests pass.

### 11. Credit cards (frontend)

Separate task, after 10 and together with task 6. Moved to the frontend task list (F7, now removed), where the account form has no `first_expense` switch, because task 10 builds only `fixed_day`. What follows is the original list.

- `types/`: `credit` account type, the card and status shapes; `lib/api/backend-contract.test.ts` must still match `0001_base.sql`.
- An icon for the type (account lists, pickers, the account form), the card fields in the account form (limit, a switch between "closes on day N of the month" and "starts when the balance goes below zero" with the day or the period length, grace days), and on the account page: available credit, spent in the period, statement balance, due date and amount due.
- Progress bar, as on debts and budgets: credit used against the limit (`-balance / limit`, capped at 100%), with the amount due marked on it when there is one. It takes the status colour (neutral for `ok`, yellow, red). Reuse the existing debt or budget progress component; the card page shows it large, lists show it compact.
- Status: a yellow triangle for `warning` and a red one for `danger` on the account in lists and on its page, with the reason in a tooltip. No dashboard block, badge counters or notifications.
- A "pay the card" action: opens the transfer form with the amount due filled in; when both accounts have the same currency the form shows one amount and an optional "commission" field (not two amounts and a rate), and saves it as the payments plus a fee line; the data model stays as it is.
- Translations, tests for the form and the status display, `npx tsc --noEmit -p tsconfig.ci.json` and the frontend tests pass.

Out of scope for good: interest, fee and minimum payment calculation, automatic pending transactions for overdue cards, notifications.
